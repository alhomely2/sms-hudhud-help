# ملاحظات الاتصال بواجهة منصة alhudhudai

تاريخ الفحص: 30 أكتوبر 2026 — بيئة الاختبار `https://staging.mytestdomain.club`.

هذه الملاحظات نتيجة فحص فعلي مباشر للخادم، لا استنتاج من وثائق. لا تحتوي على أي مفتاح فعلي؛ المفتاح المستخدم للفحص محفوظ خارج المصدر في `.tmp/` (مستثنى من التتبع) ولا يُدرج في الكود أو APK.

## 1. هوية المنصة

| العنصر | القيمة المؤكدة |
| --- | --- |
| الخادم | nginx أمام Caddy، PHP 8.2.34 |
| الإطار | Laravel 8.2.34 |
| لوحة الإدارة | Filament 3 على `/company-admin/login` |
| قاعدة مسار API | `/api/v1/` |
| فحص الصحة | `GET /up` → 200 |
| حدود المعدل | `X-Ratelimit-Limit: 300`، وتُعاد `X-Ratelimit-Remaining` |
| تتبع الطلب | `X-Correlation-Id` يُعاد في كل استجابة |

`/login` يحوّل إلى `/company-admin/login`، و`/register` يحوّل إلى `/contact`، ولا توجد صفحة توثيق API عامة (`/docs`, `/swagger`, `/openapi.json` كلها 404).

## 2. المصادقة

- الترويسة الصحيحة: `X-Api-Key`.
- شكل المفتاح: `id.secret`.
- `Api-Key` و`api_key` و`X-Authorization` غير مقروءة؛ تُعامل كأنها غائبة.

| الحالة | الاستجابة |
| --- | --- |
| بلا مفتاح | `401` و`{"success":false,"error":"مفقود في نص الطلب API مفتاح"}` |
| معرّف فقط (بدون `.secret`) | `403` و`{"success":false,"error":"API Key hash mismatch"}` |
| مفتاح غير موجود | `401` و`{"success":false,"error":"API Key غير صحيح أو غير موجود"}` |
| مفتاح صحيح | يمرّ من طبقة المصادقة ويصل إلى المتحكم |

استنتاج: المنصة تفصل بين «مفتاح مفقود» (401) و«مفتاح موجود لكن السر غير مطابق» (403)، لذا يجب عرض الحالتين بمعنيين مختلفين في التطبيق.

## 3. المسارات المتاحة

الموجود فعلاً ثلاثة عناوين فقط:

| الطريقة | المسار | الحالة |
| --- | --- | --- |
| GET, HEAD | `/api/v1/messages` | `500` |
| GET, HEAD | `/api/v1/messages/{id}` | `500` |
| DELETE | `/api/v1/messages/{id}` | `500` |

**لا يوجد مسار إرسال (`POST`) على هذه البيئة إطلاقاً.**

تنبيه منهجي: أي مسار تحت `/api/v1/messages/…` يلتقطه مسار `{id}` العام، فيظهر وكأنه موجود. الدليل أن `/api/v1/messages/send` و`/api/v1/messages/who-knows` يعيدان نفس رسالة `405`:

```
The PUT method is not supported for route api/v1/messages/send. Supported methods: GET, HEAD, DELETE.
```

لذلك لا يصح اعتبار `405` أو `500` على مسار فرعي دليلاً على وجوده. المسارات المجرَّبة خارج `/api/v1/messages` كلها `404`، ومنها: `/api/v1/send`, `/api/v1/sms/send`, `/api/v1/messages/bulk`, `/api/v1/messages/send-bulk`, `/api/v1/reports`, `/api/v1/deliveries`, `/api/v1/devices`, `/api/v2/messages`, `/api/messages`.

## 4. المشكلة الحالية: خطأ 500 على كل طلب مصادق عليه

كل طلب `GET` على `/api/v1/messages` أو `/api/v1/messages/{id}` بمفتاح صحيح يعيد:

```
HTTP/1.1 500 Internal Server Error
X-Correlation-Id: <uuid>
{ "message": "Server Error" }
```

السلوك نفسه مع كل معاملات الاستعلام المجرّبة (`page`, `per_page`, `device_id`, `company_id`, `status`, `limit`, `type`, `channel`, والتواريخ) ومع كل معرّف (`1`, `0`, `abc`). أي أن الطلب يتجاوز المصادقة ثم يفشل داخل المنصة، وليس بسبب شكل الطلب أو المفتاح.

**دليل إضافي على أن العطل بنيوي:** `DELETE /api/v1/messages/999999999` (معرّف غير موجود قطعاً) يعيد `500` بدل `404`. لو كان الربط والمفتاح سليمين لكان المتوقع `404` عند غياب السجل. النتيجة تشير إلى فشل قبل الوصول إلى السجل، وأقرب تفسير أن المفتاح لا يُحلّ إلى شركة/جهاز مرتبط، أو أن العلاقة/الجدول المطلوب غير مهيأ لهذا المفتاح.

لأن الخطأ يقع قبل إنتاج أي جسم ناجح، لا يمكن تثبيت شكل الاستجابة المتوقعة ولا شكل الترقيم ولا حقول الرسالة.

## 5. عقد الإرسال غير معروف

- `POST /api/v1/messages` → `405` نصّه: `The POST method is not supported for route api/v1/messages. Supported methods: GET, HEAD.`
- `OPTIONS /api/v1/messages` يعلن `Access-Control-Allow-Methods: POST`، لكن Laravel يرفضه؛ لا يُعتمد على preflight لاكتشاف الطرق.
- لا يوجد مسار إرسال بديل: كل المسارات المرشّحة تحت `/api/v1/messages/*` يلتقطها مسار `{id}`، وما خرج عنها يعيد `404`.
- العملية الكتابية الوحيدة الموجودة هي `DELETE /api/v1/messages/{id}`. يجب سؤال فريق المنصة عن معناها: حذف سجل فعلي، أم إقرار باستلام/إرسال رسالة؟ هذا يحدد إن كانت هي آلية «الإقرار» المطلوبة بعد الإرسال.

لا يمكن تنفيذ الإرسال أو حالة التسليم قبل أن تقدم المنصة: مسار الإرسال، شكل الطلب (أرقام، مرسل، نص، قالب)، شكل الاستجابة (معرّف الرسالة/الدفعة، معنى القبول)، وشكل تأكيد التسليم النهائي.

## 6. ما نُفّذ في التطبيق

- `RemoteEndpoint`: عنوان staging الافتراضي من `BuildConfig.HUDHUD_BASE_URL`، والترويسة `X-Api-Key`، ومسار الرسائل ومسار الصحة. ملفات المواقع الإضافية تُحفظ محليًا ولا يُنشأ عنوان إنتاج افتراضي.
- `HudhudClient.probe(apiKey)`: طلب قراءة واحد `GET /api/v1/messages` يحوّل النتيجة إلى:
  - `2xx` → `CONNECTED`
  - `401` → `AUTH_REJECTED`
  - `403` → `KEY_MISMATCH`
  - `5xx` → `SERVER_ERROR`
  - `IOException` → `NETWORK_ERROR`
  - غير ذلك → `UNEXPECTED_RESPONSE`
  ويحفظ رمز HTTP، ورسالة الخادم، و`X-Correlation-Id` ورؤوس المعدل و`Retry-After` لعرضها، مع فصل قابلية الوصول عن المصادقة وحالة endpoint. طلبات العميل لا تتبع redirects لتجنب تمرير مفتاح API لمضيف آخر.
- `ApiKeyStore`: تشفير مفتاح مستقل لكل ملف موقع بـ AES-GCM عبر Android Keystore، وعرضه مقنّعاً دون كشف السر. يرحّل المفتاح القديم إلى ملف staging عند أول قراءة.
- شاشة «إعدادات الاتصال»: إدارة ملفات HTTPS والموقع النشط والمفاتيح، وضبط مهلات الاتصال ومعدل/حجم الطلب المقترح. إعداد الدفعة والمحاولات محفوظ فقط؛ لا توجد عملية رفع أو إرسال لتطبيقهما بعد.
- حملات الرسائل الجاهزة تُحفظ محلياً في Room مع رسائلها على دفعات، وتظهر في قائمة الحملات بحالة «جاهزة محلياً» أو «تحتاج مراجعة».
- إضافة الحملة إلى القائمة لا ترسلها إلى المنصة؛ يظل الإرسال معطلاً حتى توفر المنصة عقد إرسال موثقاً.
- لا منطق إرسال أو إعادة إرسال في هذه الطبقة.

## 7. المطلوب من فريق المنصة

1. إصلاح خطأ `500` على `GET /api/v1/messages` والمسارات الفرعية، أو تزويدنا بـ`X-Correlation-Id` من طلب فاشل لمراجعته في سجلاتهم. آخر معرّفات للتتبع: `875ae55c-4456-4811-bff5-8f978a1942cd` (DELETE لمعرّف غير موجود)، و`d82f3618-7759-4bdd-ad88-fb5beac14433` (GET القائمة).
2. التأكد من أن المفتاح `Q9FXFDJD…` مرتبط بشركة وجهاز نشط؛ `DELETE` على معرّف غير موجود يعيد `500` بدل `404`، وهذا يرجّح فشلاً في حلّ المفتاح إلى كيانه قبل الوصول إلى السجل.
3. توفير مسار الإرسال: الطريقة، المسار، شكل الطلب (رقم، نص، مرسل، معرّف دفعة)، وشكل الاستجابة (معرّف الرسالة/الدفعة، معنى القبول).
4. توضيح دلالة `DELETE /api/v1/messages/{id}`: حذف فعلي أم إقرار استلام؟ وإن كانت الثانية فهي آلية الإقرار التي سنستخدمها.
5. توثيق تقرير التسليم: هل يُقرأ من `GET /api/v1/messages` نفسه أم من حقل حالة داخل كل رسالة؟ وما القيم الممكنة؟

## 8. إعادة الفحص

```powershell
$key = (Get-Content D:\sms-hudhud-help\.tmp\api-key.txt -Raw).Trim()
curl.exe -sS -i -H "X-Api-Key: $key" -H "Accept: application/json" `
  https://staging.mytestdomain.club/api/v1/messages
```

عند تحسّن الاستجابة إلى `2xx` يُثبَّت شكل الجسم في اختبارات `HudhudClientTest` ويُضاف منطق الإرسال وفق العقد الموثق.
