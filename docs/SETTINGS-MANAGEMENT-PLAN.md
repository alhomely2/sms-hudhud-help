# خطة تطوير نظام الإعدادات والتحكم في الإرسال (Settings & Throttle Management Plan)

**الحالة:** نُفذت إعدادات الاتصال المحلية ومراحل التهيئة؛ رفع الحملات والإرسال والتسليم مؤجلة إلى حين اعتماد عقد المنصة.  
**النطاق:** إدارة اتصالات مواقع المنصة، حفظ مفاتيحها، وضبط مهلات ومعدل/حجم الطلبات. لا تعني الإعدادات أن واجهة الإرسال متوفرة.

---

## 1. الدواعي والأهداف
- إدارة اتصال واحد أو أكثر بمواقع المنصة من إعدادات واضحة، مع حفظ ملف مستقل لكل موقع واختيار الموقع النشط.
- ضبط معدل الطلبات وحجم كل دفعة وفق حدود كل موقع، مع احترام حدود الخادم وعدم اعتبار الإعدادات بديلاً عنها.
- إبقاء إعداد المفتاح والاختبار الحاليين عاملين، وعدم تفعيل رفع الحملات أو إرسال الرسائل قبل توثيق عقد API واختباره.
- فصل إعدادات نقل البيانات إلى الموقع عن حجم دفعات إدراج الرسائل في قاعدة البيانات المحلية؛ فهما عمليتان مختلفتان.

---

## 2. الوضع الحالي والقيود المؤكدة

| المجال | الموجود الآن | الفجوة |
|---|---|---|
| الإعدادات العامة | `AppSettingsStore` يخزن ملفات المواقع النشطة وإعدادات الفاصل (0–60 ثانية)، وحجم الدفعة (10–500)، والمحاولات، والمهلات في `SharedPreferences`. | الفاصل والمحاولات وحجم الرفع إعدادات محفوظة فقط؛ لا يوجد تدفق إرسال يستهلكها بعد. |
| ترحيل الإعدادات | تُحوّل مفاتيح delay/batch/retry القديمة إلى ملف staging، وتُقيد القيم الخارجة عن الحدود مع إشعار مرة واحدة. | مفتاح API القديم يُنقل عند أول قراءة للموقع الافتراضي. |
| مفتاح API | `ApiKeyStore` يشفر مفتاحًا مستقلًا لكل ملف موقع بـ AES-GCM ومفتاح Android Keystore، ويعرضه مقنّعًا. | لا يُدرج المفتاح في كائن الملف أو سجل التطبيق. |
| ملفات المواقع | يمكن إضافة/تعديل/حذف ملفات HTTPS واختيار موقع نشط. لا يُنشأ عنوان إنتاج تخميني. | على مالك المنصة تزويد عنوان الإنتاج الصحيح قبل إضافته. |
| اختبار الاتصال | `HudhudClient.probe` يرسل طلب GET للقراءة فقط، ويعرض الوصول/المصادقة/حالة API منفصلة ورؤوس المعدل و`X-Correlation-Id`. العميل لا يتبع redirects. | المسار المعتمد يعيد `500` في فحص البيئة الموثق، لذا لا تعتبر نتيجة probe نجاحًا وظيفيًا. |
| مهلات الاتصال | مهلات connect/read/call قابلة للتعديل ضمن نطاقات محددة ومخزنة لكل ملف موقع. | لا تُغير المهلات سلوك إرسال غير موجود. |
| دفعات التخزين المحلي | `CampaignStorage` يدرج رسائل Room في مجموعات ثابتة من 200 سجل. | هذا حد إدراج محلي مستقل عن إعداد حجم الرفع (10–500) ولا يُغيّر عبره. |
| رفع الحملات والإرسال | الحملات ورسائلها تحفظ محليًا؛ لا يوجد منطق إرسال أو إعادة محاولة. | فحص المنصة لا يثبت مسار كتابة صالحًا. `POST /api/v1/messages` غير مدعوم، وعقد الرفع والإرسال والتسليم غير موثق. |

تفاصيل عقد المنصة ونتائج فحصها في [ملاحظات الاتصال](./API-CONNECTION-NOTES.md). لا يُسمّى الموقع «متصلًا بالكامل» لمجرد نجاح DNS أو `/up`؛ يجب عرض الوصول، المصادقة، وتوفر الوظيفة كحالات مستقلة.

## 3. السلوك المستهدف ونطاق الإعدادات

تكون الشاشة عربية وRTL، وتقسم الإعدادات إلى مجموعات مستقلة:

### أ. ملفات المواقع والاتصال

- ملف لكل موقع يتضمن اسمًا وصفيًا، عنوان أساس، مفتاح API، وبيانات اتصال الموقع. يبدأ التطبيق بملف staging الحالي؛ تُضاف بيئة الإنتاج فقط بعد تزويد مالك المنصة بعنوانها وعقدها.
- اختيار موقع نشط صريح، وعرضه بوضوح في شاشة الاتصال والحملة قبل أي عملية شبكية.
- تحرير/إضافة/حذف ملف الموقع مع تأكيد قبل الحذف؛ لا يُحذف الملف النشط دون اختيار بديل أو تأكيد مناسب.
- قبول HTTPS فقط في نسخ الإنتاج، ورفض بيانات اعتماد مضمنة في URL والمسارات غير الصالحة. لا يُرسل المفتاح إلى عنوان غير محفوظ/غير مؤكد، ولا تتبع إعادة توجيه إلى مضيف آخر مع بيانات الاعتماد.
- مفاتيح منفصلة لكل موقع، محفوظة ومقنّعة عبر Android Keystore؛ لا تظهر في السجلات أو رسائل الخطأ أو النسخ الاحتياطي.
- مهلات اتصال وقراءة قابلة للضبط ضمن حدود آمنة. لا يتحول ضبط المهلة إلى تعطيل مهلة الطلب الكلية أو انتظار غير محدود.
- اختبار اتصال يوضح على حدة: الوصول إلى المضيف، قبول المفتاح عند توفر endpoint موثق، وحالة خدمة API. يعرض HTTP status و`X-Correlation-Id` والتفصيل المنقح دون كشف المفتاح.

### ب. معدل الطلبات إلى كل موقع

- فاصل أدنى بين طلبات الدفعات، ومحاولات إعادة محدودة؛ تطبق القيم على ملف الموقع المحدد ولا تُفترض حدود موحدة بين المواقع.
- أوضاع اختيارية مبسطة (هادئ/متوازن/أسرع) تكون اختصارات لقيم محددة وآمنة، مع إظهار القيم الفعلية وحدودها؛ لا تسمح بتجاوز حد الموقع المعروف.
- عند استلام `429` أو `Retry-After` أو ترويسات معدل موثقة، يحترم العميل إشارة الخادم ويؤخر العمل. حد `X-Ratelimit-Limit: 300` المرصود لا يحدد وحده فترة القياس، لذا لا يُفسر كـ300 طلب/دقيقة دون تأكيد.
- إعادة المحاولة فقط للأخطاء العابرة المصنفة بعد توثيق العقد. أخطاء المصادقة والتحقق لا تعاد آليًا. نتيجة الطلب الملتبسة لا تعاد إذا كان ذلك قد يكرر إرسال رسائل دون دعم idempotency من الخادم.

### ج. حجم الدفعة إلى الموقع

- يحدد لكل موقع عدد الرسائل/السجلات في طلب الرفع الواحد، ويكون مستقلًا عن دفعات Room الداخلية وعن عدد الرسائل المعروضة في الصفحة.
- لا يُفعّل حقل حجم دفعة الإرسال إلى حين توثيق الحد الأقصى من المنصة ودلالة كل عنصر في الطلب. يكون الحجم الفعلي `min(إعداد المستخدم، الحد الموثق للخادم)`؛ لا يخمّن التطبيق حدًا أعلى.
- تُحفظ الدفعة والنتيجة ومعرّف الطلب/الدفعة لكل محاولة بما يكفي للاستئناف ومنع إرسال العناصر المقبولة سابقًا مرة أخرى.
- إعداد الحجم الحالي (10–500، افتراضي 50) لا يُنقل آليًا إلى حد إرسال خارجي قبل موافقة المنصة. يظل حد إدراج Room الداخلي (200) منفصلًا، ويضبط داخليًا أو عبر إعداد أداء مستقل عند وجود حاجة مثبتة.

### د. إعدادات الحملة والصيانة

- إظهار الموقع النشط، وعدد العناصر الجاهزة والمراجعة، وحجم الدفعة المتوقع قبل بدء العمل.
- حفظ حالات الحملة محليًا مع فصل: «محفوظة محليًا»، «قيد الرفع»، «قبلتها المنصة»، «إرسال الرسائل»، و«تسليم الرسائل». لا تنتقل حالة إلى أخرى دون استجابة/تأكيد موثق.
- لا يُضاف حذف تلقائي للسجلات أو مسح عام للبيانات في هذه المرحلة. أي تنظيف لاحق يكون عملية منفصلة، مع معاينة وتأكيدة صريحة، ولا يحذف مفاتيح أو حملات نشطة ضمنًا.

## 4. القرارات المعمارية المقترحة

1. **مصدر الإعدادات:** يستخدم التنفيذ الحالي `AppSettingsStore` و`SharedPreferences` لتجنب اعتماد جديد ولتوافقه مع الإعدادات الحالية. تبقى الأسرار في `ApiKeyStore` المشفر بواسطة Android Keystore؛ لا تُخزّن المفاتيح داخل كائن إعدادات عادي.
2. **توافق البيانات:** ترحّل قيم `AppSettingsStore` القديمة إلى ملف staging، وتُقيد القيم الخارجة عن النطاق مع إشعار مرة واحدة. يُنقل المفتاح القديم إلى ملف staging عند أول قراءة، دون كشفه أو طلب إدخاله مجددًا. تبقى الأسرار خارج النسخ الاحتياطي حسب سياسة Android الحالية.
3. **ملفات المواقع:** معرف ثابت لكل ملف واتصال، وموقع نشط واحد لكل عملية تشغيل/حملة. إعدادات المعدل والحجم تخص الملف نفسه. تُحفظ بيانات التعريف في مخزن الإعدادات، والمفتاح في مخزن الأسرار بمفتاح يطابق معرف الموقع.
4. **فصل المسؤوليات:** مكونات مستقلة لإدارة ملفات الاتصال، اختبار الاتصال، سياسة معدل الطلب، وتدفق رفع/إرسال الحملة؛ لا تُضاف هذه العمليات كمنطق مركزي إلى `ConnectionSettingsActivity`.
5. **عميل الشبكة:** إنشاء عميل/إعداد طلب من ملف الموقع الفعال، مع TLS الافتراضي لـOkHttp، مهلات مضبوطة، وعدم تسجيل Authorization/API keys أو نصوص الرسائل وأرقام الهاتف. الاحتفاظ بمعرفات الارتباط المنقحة لتشخيص الأعطال.
6. **عمل طويل الأمد:** بعد ثبوت عقد الإرسال، استخدام عمل موثوق قابل للاستئناف (مثل WorkManager) مع إشعار تقدم وإيقاف آمن، وتخزين نتيجة كل دفعة. لا يطلق عمل خلفي إرسالًا فعليًا قبل تأكيد المستخدم.
7. **عدم إضافة اعتماد لمجرد التخطيط:** يعتمد DataStore/WorkManager أو غيرهما عند بدء المرحلة التي تحتاجه وبعد فحص ما هو موجود محليًا؛ لا تنزيل أو تثبيت ضمن إعداد الخطة.

## 5. مراحل التنفيذ والبوابات

### المرحلة 0 — تثبيت العقد والبيئات (مانعة للإرسال)

- [ ] استلام عنوان كل موقع مسموح استخدامه، وبيئة staging للاختبار، وعنوان الإنتاج المؤكد.
- [ ] توثيق المصادقة، endpoint وطريقة رفع الدفعة، مخطط الطلب والاستجابة، أقصى حجم، معنى قبول الرسالة، حدود المعدل وفترتها، و`Retry-After`.
- [ ] توثيق idempotency واستعلام حالة الدفعة/الرسائل وحالات التسليم؛ تحديد سلوك مهلة الشبكة بعد أن يكون الخادم قد قبل الطلب.
- [ ] معالجة خطأ `500` الحالي في `GET /api/v1/messages` مع فريق المنصة؛ لا يُستخدم نجاح اتصال ظاهري كبديل عن إصلاحه.
- **بوابة الخروج:** لا رفع ولا إرسال قبل وجود عقد مكتوب واختبار staging ناجح. يمكن تنفيذ إعداد الملفات المحلية واختبار الوصول بمعزل عن الإرسال.

### المرحلة 1 — نموذج الإعدادات والتخزين

- [x] تعريف `SiteProfile` والتحقق المركزي من العنوان والمهلات والفاصل والحجم والمحاولات.
- [x] ترحيل إعدادات SharedPreferences القديمة إلى ملف staging، مع ترحيل المفتاح القديم عند أول قراءة.
- [x] إزالة ملف الإنتاج الافتراضي القديم غير المؤكد عند الترقية، وإرجاع الموقع النشط إلى staging.
- [x] إظهار أخطاء الإدخال في الحقول، وعدم استبدال المدخلات الحالية بالقيم الافتراضية بصمت.
- [x] تقييد القيم القديمة الخارجة عن الحدود وإظهار إشعار مرة واحدة؛ اختبارات ترحيل الإعدادات موجودة.

### المرحلة 2 — واجهة إدارة المواقع والاتصال

- [x] تنظيم الشاشة إلى ملفات المواقع، المهلات، معدل الطلبات/الدفعات، والصيانة.
- [x] إضافة/تعديل/تحديد/حذف ملفات المواقع؛ لا يمكن حذف الموقع النشط أو تفعيل ملف معطّل.
- [x] إدارة مفتاح مستقل لكل موقع مع حفظ/مسح وقناع آمن.
- [x] عرض الوصول والمصادقة وحالة API منفصلة، وتعطيل زر الاختبار أثناء الطلب.
- [x] توطين عناصر الشاشة وأخطاء التحقق ودعم RTL.

### المرحلة 3 — تهيئة العميل والتحكم بالمعدل

- [x] تمرير ملف الاتصال المختار إلى عميل probe بدل استخدام عنوان عام للطلب.
- [x] منع اتباع redirects عند إرسال مفتاح API، وفرض HTTPS عند حفظ ملف الموقع، وضبط مهلات العميل من الملف.
- [x] تحليل `Retry-After` ورؤوس المعدل وعرضها، وتوفير حساب backoff/إعادة المحاولة مع اختبارات وحدات.
- [ ] لا يُطبق انتظار/محدد معدل على رفع حملات؛ لا توجد عملية رفع حالية. يُربط المنظم بطلبات الرفع بعد اعتماد العقد، ولا تُعاد محاولات probe تلقائيًا.
- [x] إبقاء probe للقراءة فقط على المسار الحالي.

**حالة التحقق (31 أكتوبر 2026):** نجح `:app:processDebugResources` والاختبار الكامل والبناء `:app:testDebugUnitTest :app:assembleDebug`؛ اجتازت الاختبارات الـ93 دون إخفاق، وأُنتج APK للتصحيح. شملت إصلاحات موانع البناء موارد الألوان والأنماط الناقصة، وبنية `strings.xml` وتكرار اسم مورد، ومراجع نموذج الاستيراد، وتوجيه الشاشة الرئيسية إلى مساري استيراد موجودين. بقيت بوابة عقد API كما هي؛ نجاح البناء لا يفعّل رفع الحملات أو إرسال الرسائل.

### المرحلة 4 — ربط الدفعات المحلية بالرفع (بعد اجتياز المرحلة 0)

- [ ] إضافة عقد API الموثق typed models وعميل منفصل لوظيفة الرفع؛ لا توسيع probe ليصبح مرسلًا.
- [ ] إنشاء دفعات ثابتة من عناصر الحملة ذات الحالة الجاهزة فقط، مع فحص وجهة الموقع ومراجعة الحملة قبل أول طلب.
- [ ] حفظ حالة كل دفعة ومعرفاتها واستجابتها، ودعم استئناف آمن وحالات جزئية دون إعادة العناصر المقبولة.
- [ ] تطبيق إعادة المحاولة المحدودة للتصنيفات العابرة فقط، مع backoff واحترام ترويسات الخادم وidempotency.
- [ ] إضافة تأكيد مستخدم واضح قبل بدء الرفع، ومؤشر تقدم، وإلغاء/استئناف، وتقرير نتائج نهائي.
- [ ] إبقاء الإرسال معطلاً افتراضيًا في الإصدارات حتى اجتياز staging وموافقة مالك المنتج على عقد الإنتاج.

### المرحلة 5 — التسليم والتشغيل

- [ ] ربط حالات التسليم فقط بمصدر بيانات موثق من المنصة، مع التمييز بين قبول المنصة والتسليم النهائي.
- [ ] تشغيل اختبارات staging بحساب/مفتاح مخصص غير إنتاجي، ثم إطلاق تدريجي مع حدود محافظة ومراقبة الأخطاء.
- [ ] تحديث دليل المستخدم و`README.md` وملاحظات API بعد اعتماد السلوك النهائي.

## 6. استراتيجية الاختبار ومعايير القبول

### الاختبارات المطلوبة

- Unit: القيم الافتراضية والحدود والتحقق، حفظ/تحميل/ترحيل الإعدادات، ربط الأسرار بمعرف الموقع، اختيار الموقع النشط، إنشاء دفعات بالحجم المسموح.
- Unit للشبكة باستخدام `Call.Factory` وهمي: ترويسة المفتاح للمضيف المقصود فقط، HTTPS، نتيجة 2xx/401/403/429/5xx/network timeout، `Retry-After` ومعرف الارتباط، ورفض إعادة الطلب الملتبس دون idempotency.
- Integration: الترحيل من تفضيلات الإصدار الحالي، حفظ حملات كبيرة على دفعات محلية، نتائج دفعات جزئية واستئنافها، وعدم إرسال حملة تحتوي رسائل تحتاج مراجعة.
- واجهة/يدوي على staging: ملفات مواقع متعددة، تبديل الموقع، حفظ مفتاح مستقل، وضوح الاتصال النشط، RTL، وظهور الأخطاء دون كشف السر.
- Regression: إنشاء حملة وحفظها محليًا يظل ممكنًا حتى عند عدم توفر الشبكة؛ اختبار الاتصال لا يغير الحملات؛ الإعدادات الحالية لا توهم بأن الإرسال مفعل.

### معايير القبول

- تبقى الإعدادات والمفاتيح صحيحة بعد إغلاق التطبيق وتحديثه، ولا يظهر أي مفتاح كامل في UI أو logs أو crash reports.
- لا ينتقل أي طلب إلى موقع غير الملف النشط، ولا تُرسل بيانات اعتماد عبر HTTP أو بعد redirect لمضيف غير معتمد.
- حجم طلبات المنصة يطابق إعداد الموقع وحد الخادم الموثق، ولا يخلط مع دفعة Room الداخلية.
- لا توجد إعادة إرسال مكررة بعد انقطاع أو استئناف؛ إذا تعذر ضمان ذلك بالعقد، تتوقف العملية بحالة تحتاج مراجعة وتطلب تدخل المستخدم.
- لا توجد عبارة «أُرسلت» أو «سُلّمت» قبل تأكيد موثق يطابق هذه الحالة.
- جميع اختبارات الوحدة والتكامل المستهدفة ناجحة، ثم ينجح بناء التطبيق واختبار staging قبل تفعيل الرفع.

## 7. المخاطر والقرارات المطلوبة من مالك المنتج/المنصة

| السؤال | التوصية الافتراضية حتى الإجابة |
|---|---|
| هل يدعم التطبيق عدة مواقع فعلًا أم staging/production فقط؟ | ملف staging مبدئيًا، وتُضاف المواقع الأخرى بعنوان مؤكد يقدمه المستخدم/مالك المنصة؛ لا يُخترع عنوان إنتاج افتراضي. |
| هل حجم الدفعة لكل موقع أم عام؟ | لكل ملف موقع، مع حد أعلى يفرضه عقد ذلك الموقع. |
| ما الحدود النهائية للفاصل والمهلات والمحاولات؟ | لا تعتمد الأرقام الحالية كحدود API؛ تؤخذ من عقد المنصة وتجربة staging. |
| ما الحد الأقصى للدفعة وفترة rate limit؟ | لا يمكن استنتاجها من ترويسات الفحص الحالية؛ يجيب فريق المنصة. |
| هل API يرفع حملة أم يرسل SMS مباشرة؟ | عمليتان مختلفتان؛ لا يُعرض نجاح الأولى كنجاح للثانية. |
| هل يسمح المنتج بتغيير عنوان الموقع من واجهة المستخدم؟ | العنوان الافتراضي ثابت/موثوق؛ أي عنوان مخصص يحتاج HTTPS وموافقة واضحة وتدقيق أمني. |
| هل يمكن تكرار طلب بعد انقطاع؟ | فقط بدعم idempotency/استعلام الحالة؛ وإلا تُعلّق الدفعة الملتبسة للمراجعة. |

## 8. قائمة التحقق التنفيذية

1. [x] إنشاء وثيقة الخطة (`docs/SETTINGS-MANAGEMENT-PLAN.md`).
2. [ ] تثبيت عقد API والبيئات وحدود كل موقع (بوابة قبل الرفع والإرسال — بانتظار تزويد فريق المنصة لعقد الإرسال).
3. [x] بناء نموذج/مستودع إعدادات مع ترحيل متوافق ومخزن أسرار لكل موقع (`SiteProfile`, `AppSettingsStore`, `ApiKeyStore`).
4. [x] تنفيذ واجهة ملفات المواقع والاتصال والتحقق والتوطين (`ConnectionSettingsActivity`, `dialog_site_profile.xml`, `strings.xml`).
5. [x] تطبيق مهلات العميل وسياسة المعدل/إعادة المحاولة كوحدات قابلة للاختبار، وعرض إشارات الخادم (`RequestThrottlePolicy`, `ThrottlePreset`, `HudhudClient`). (تطبيق المنظم على تدفق إرسال مؤجل لغياب عقد الإرسال.)
6. [x] توثيق وفصل دفعات التخزين المحلي عن دفعات الموقع وربط إعدادات كل منهما بمسؤوليتها (`CampaignStorage`, `AppSettingsStore`).
7. [ ] تنفيذ الرفع والاستئناف وإعادة المحاولة فقط بعد اعتماد العقد واجتياز الاختبارات (مؤجل حتى توثيق مسار POST).
8. [ ] تمكين حالات التسليم فقط بعد توفر endpoint موثق، ثم مراجعة وتحديث الوثائق.
